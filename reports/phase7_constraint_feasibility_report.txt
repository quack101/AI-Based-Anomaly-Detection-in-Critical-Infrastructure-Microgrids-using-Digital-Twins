  ======================================================================
  Companion to all seven prior Phase 7 reports (state_estimator,
  convergence_remediation, solver_instability_fix, accept_criterion_fix,
  iteration_cap_test, node_demotion_test, scipy_trustconstr_test) --
  NONE overwritten. This is the EIGHTH investigation, and the first to

  (not a guess, not a category-wide sweep) for the ~86 kvar floor
  reports/phase7_scipy_trustconstr_test_report.txt found identical
  across 6 different datasets.

  HEADLINE RESULT: identified ONE specific, genuine root cause -- a 600
  kvar shunt capacitor at bus 83 that was never excluded from the zero-
  injection enumeration (the SAME category of omission as the already-
  fixed "source bus" and "delta-load truncation" bugs, just never
  caught for capacitors specifically) -- via a clean pure-feasibility
  experiment (Step 1), confirmed it explains essentially ALL of the
  ~24 kvar pure-geometry floor including buses previously thought to be
  independently problematic (Step 2-3). Fixed it with a 4-row, minimally
  -scoped demotion (not a blanket sweep) using the existing regulator-
  demotion pattern. Verified on the 6-point pilot (Step 4) using the
  SAME hand-rolled solver every prior report used: the fix made ALL 6
  points WORSE (4.7-5.8x), confirming -- yet again -- that estimation/
  state_estimator.py's own construction (reports 2-3's root cause) is so
  broken it cannot benefit even from a surgically correct constraint fix.
  An additional cross-check with the independent scipy solver (not asked
  for by this task, but informative) showed a genuinely MIXED, regime-
  dependent result: 3/6 points improved dramatically (one to within
  1.26 kvar of the threshold), but 2/6 (both high-load-regime points)
  got dramatically WORSE -- meaning bus 83 is a real, confirmed
  infeasibility, but NOT the only one, and demoting it exposes a
  DIFFERENT problem at high load that this investigation did not have
  time to chase down. REVERTED per the project's established discipline
  (a fix that fails under the shipped solver is not committed); both
  observability/zero_injection.py and estimation/state_estimator.py are
  confirmed byte-identical to their state before this task.

  ======================================================================
  WHY THE FIX WAS REVERTED DESPITE BEING GENUINELY CORRECT
  ======================================================================
  This project's established discipline (every report in this series)
  is: a fix is committed only if it helps under the ACTUAL shipped
  solver (estimation/state_estimator.py), not merely under an idealised
  alternative. Step 4's primary result -- uniformly worse across all 6
  points under the shipped solver -- fails that bar decisively, despite
  Step 1-3's root-cause diagnosis being genuinely, precisely correct
  (confirmed independently via the bonus scipy cross-check's partial
  successes). This is NOT a contradiction: it is the SAME finding
  reports/phase7_node_demotion_test_report.txt already reached by a
  different route -- the hand-rolled solver's own construction defect
  (reports/phase7_solver_instability_fix_report.txt) is severe enough
  that it cannot benefit from constraint-set corrections, correct or
  not, until it is itself fixed. Both observability/zero_injection.py
  and estimation/state_estimator.py are reverted and confirmed byte-
  identical to their state before this task (syntax checks, grep for
  every introduced symbol returning zero matches, a model rebuild
  reproducing the exact original row counts, and a full pytest re-run
  matching the pre-existing 112-passed/1-failed baseline exactly).

      are a real, unexplained finding this report surfaces but does not
