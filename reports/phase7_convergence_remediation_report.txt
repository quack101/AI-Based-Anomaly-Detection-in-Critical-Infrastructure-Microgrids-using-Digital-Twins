Iteration count is FLAT AT 30 (the cap) across every delta, INCLUDING
delta=0 -- so by the task's own flat-vs-rising test on ITERATION COUNT
alone, this reads as "not circular" (correct, confirming Step 1).
BUT iteration count is the wrong lens here, because nothing ever

why. Neither holds. Instead, reading constraint_residual_inf and

(delta=0.01/0.05/0.10 stay in the same 5x10^6-6x10^7 kvar range, not a
smooth continuation of the trend). This is an abrupt, two-sided cliff,
not a monotonic "harder start = slower convergence" curve: a
near-perfect start is fine-ish, and ANY tested perturbation away from
it is catastrophic, reproduced independently at two different
timestamps (different hour-of-day, different load tertile).

This pattern matches the SPECIFIC failure mode estimation/
state_estimator.py's own module docstring describes under "REMEDIATION
(Phase 7 review, Block 2.1)" as the motivation for the step-fraction/
ratchet-divergence fix -- A_reduced's extreme ill-conditioning
(cond~2e22 documented there) amplifying small inconsistencies in
b_reduced into a numerically meaningless `w` -- and the docstring's own
"BUG FOUND AND FIXED HERE" / "SECOND BUG FOUND AND FIXED HERE" notes
describe a near-identical historical failure (16.2 million kvar,
1.03 pu error) that was supposedly already fixed. This diagnostic shows
that failure mode, or one with the same signature, is STILL
REACHABLE from a near-truth starting point under the currently shipped
code -- the fix documented in the module's own docstring did not fully
close it. This is a NEW finding from this diagnostic, not a restatement
of the original report's known bus-83 residual.

STEP 4 -- CONVERGENCE-CRITERION FIX, BEFORE/AFTER
======================================================================
The combined criterion (||dx|| < tol AND constraint_residual < tol_c)
is ALREADY the shipped default in the current estimation/
state_estimator.py (DEFAULT_TOL_CONSTRAINT_KW=1.0, set by a prior,
uncommitted pass -- see this report's opening scope note). This
section ISOLATES that criterion change from the OTHER fixes bundled
into the same file (LM damping, ratchet-divergence fix, step-fraction
search) by calling the SAME current solver twice per sampled point --
once with tol_constraint_kw=inf (reproduces the OLD, step-size-only
stopping rule exactly, on top of the CURRENT solver internals) and once
with the shipped default -- rather than re-running the stale
2026-08-30 pre-LM-damping CSVs, which would confound the criterion
change with those other fixes. Same 30-point stratified sample, flat
start (condition A) at every point for both columns, so the only
difference between them is the stopping rule. Scripts:
validation/phase7_old_criterion_only.py (fresh run) +
validation/phase7_stratified_AB.py's A_flat rows (already-collected
"after"). Full record: validation/phase7_old_criterion_results.csv.

THRESHOLD CHOSEN: tol_constraint_kw = 1.0 kW/kvar (already set in the
shipped code, not changed by this report). Justification, read from
the code's own comment (estimation/state_estimator.py:199-214): tight
relative to real nodal load magnitudes on this feeder (tens to hundreds
of kW/kvar) and to the ~200 kvar failure it targets, while loose enough
that float64 rounding noise never forces a spurious extra iteration
(94.8% of the 328 hard rows already sat under 0.01 kW/kvar even before
the LM fix, per the original report Part D.2). Neither Sha25 nor
Sayghe gives a numeric constraint-residual stopping threshold directly
-- this is an engineering judgment call against the feeder's own load
scale, stated as such, not sourced to either paper.

  criterion              n   conv.   iters(mean/median/max)   max_v_err_pu(mean/max)   constraint_residual_inf(mean/median/max/min)
  OLD (step-size only)   30  30/30   8.33 / 8 / 11            0.0434 / 0.0621          128.91 / 134.19 / 154.16 / 111.89
  NEW (step-size+constr) 30   0/30   30.0 / 30 / 30           0.0429 / 0.0623          100.36 / 99.50 / 118.33 / 84.22

Before/after reading: the OLD criterion, even running through the
CURRENT (already LM-damped) solver internals, "converges" at a mean of
8.33 iterations -- NOT the original report's "mean 1.00" (that number
was a property of the ORIGINAL, non-LM-damped solver + loose criterion
combination; the LM damping itself makes each step more conservative,
so even step-size convergence now takes longer). Critically, the OLD
criterion's declared-converged constraint residual (mean 128.9, max
154.2 kvar) is NOT better than, and is in several cases WORSE than,
what the NEW criterion achieves by brute-forcing all 30 iterations
(mean 100.4, max 118.3 kvar) -- i.e. the combined criterion's extra
iterations DO measurably shrink the constraint violation (129 -> 100
kvar on average) but never enough to clear its own 1.0 kvar bar within
the shipped 30-iteration cap. The fix is doing real, directionally
correct work; the iteration cap is simply too small for this feeder's
reduced-system conditioning, OR (per Step 3) the solver has a deeper
stability problem that more iterations alone would not fix.

VERDICT
======================================================================
RETRACT the original "100% convergence, mean 1.00 Gauss-Newton
iterations" headline (reports/phase7_state_estimator_report.txt Part
C.3) rather than merely caveat it. Reasons, in order of severity:

1. The number was measured under a stopping rule (||dx|| < tol alone)
   that is now independently shown, by this report's own corrected
   criterion, to declare "converged" while 2+ of 328 supposedly EXACT
   hard zero-injection constraints sit ~100-200 kvar off target --
   not a rounding-scale violation on a feeder whose real nodal loads
   are tens-hundreds of kW/kvar. "Converged" did not mean what the
   estimator's own design (Sha25 Sec II eq. 1-6, hard EXACT equality
   constraints) requires it to mean.

2. Under the corrected criterion, convergence rate is 0% (0/30) on a
   load-stratified sample spanning the full TEST-split day, for BOTH
   a flat start and a realistic causal warm start -- this is not an
   edge case or a single bad timestamp, it reproduces identically
   across all three load regimes tested.

3. The circularity question itself is answered NO (Step 1, confirmed
   by Step 3's delta=0 point) -- but Step 3 surfaces a materially
   WORSE finding than either of the task's two hypothesized
   explanations: a small (0.1%) perturbation away from the exact true
   state triggers a 3-4-order-of-magnitude constraint-residual blowup
   and near-saturated state error, reproduced at two independent
   timestamps. This looks like the SAME ill-conditioned-reduced-system
   failure mode the code's own docstring describes fixing (Block 2.1)
   -- evidence that fix is incomplete, not evidence of a new, unrelated
   bug, but incomplete all the same.

4. This is independently corroborated by a currently-FAILING test in
   the existing suite (test_recovers_x_true_on_normal_timestamp,
   1 failed / 112 passed) -- not a number this report invented, a
   regression already present in the committed test file against the
   currently shipped estimator code.

The underlying WLS/null-space/hard-constraint FORMULATION (Part A of
the original report) is not challenged by this audit -- only the
CONVERGENCE/ITERATION-COUNT claim, and the convergence-criterion fix
built on top of it, are retracted pending further work. Recommended
next step (not implemented here -- redesigning the solver further is
outside this audit's scope): root-cause why a near-x_true perturbation
diverges rather than contracts under the LM-damped null-space step,
likely requiring either a smaller trust-region cap specifically for the
first few iterations, a different (e.g. Tikhonov on A_reduced AND
y_particular jointly, not just A_reduced) damping scheme, or accepting
a larger max_iter with evidence it eventually contracts rather than
oscillates.
