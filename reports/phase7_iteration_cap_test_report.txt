This report tests a DIFFERENT question than the prior four: those all
targeted the ADVERSARIAL circularity-diagnostic repro point (i=46,
delta_frac=0.001 -- a synthetic 0.1% independent-per-node perturbation
from x_true, a worst-case stress test). This report asks whether the
REALISTIC stratified sample (flat start, real Phase-6 corpus
timestamps, NOT a synthetic perturbation) merely needs MORE iterations
-- zero other code changes -- to cross the ~1 kvar convergence
threshold.

HEADLINE RESULT: NO. Raising the iteration cap 5x (30 -> 150), with
the single-line diff confirmed and nothing else touched, produced
ZERO improvement at ALL 6 pilot points (2 per load regime: low, mid,
high) -- every single point's constraint_residual_inf at iteration 150
is BIT-IDENTICAL to its value at iteration 30 (the original
remediation audit's own number). The solver reaches a genuine FIXED
POINT well before iteration 30 at every tested point; iterations 31-150
did not move the state AT ALL, they only burned wall-clock time (each
point took 595-891 seconds for 150 iterations -- 5-7x the original
~50-130s for 30 -- to achieve literally nothing). Per the pre-declared
decision rule, STOPPED HERE: the full 30-point re-run and pytest were
NOT run, since the pilot already shows the "no improvement" branch of
the decision point unambiguously. estimation/state_estimator.py is
reverted and confirmed byte-identical to its state before this task.
RECOMMENDATION: do not pursue a larger iteration cap (300/500/1000)
without first explaining WHY the solver reaches a true fixed point,
not merely a slow approach -- raising the cap further without that
explanation is exactly the "guessing" the task's own decision rule
warned against.

======================================================================
WHY THIS HAPPENS -- MECHANISM, CONSISTENT WITH THE PRIOR FOUR REPORTS
======================================================================
This fits the EXACT "no improving step found" branch estimation/
state_estimator.py's existing code already names and handles
explicitly (the `if not improved: dx_v = zeros(...)` branch, documented
in that module's own "BUG FOUND AND FIXED HERE" comment): once NO
(lambda, frac) combination in the nested retry loop produces a
cand_merit below current_merit, the code takes NO step for that outer
iteration (by design, to avoid the ratchet-divergence bug a prior pass
fixed) -- but lm_lambda carries over AT ITS MAXED VALUE (LM_LAMBDA_MAX=
1e18) into the NEXT outer iteration. Once a point reaches this state,
EVERY subsequent outer iteration re-solves the SAME (unmoved) point's
Newton step at an ALREADY-MAXED lambda, exhausts LM_MAX_TRIES=15 tries
immediately (lambda cannot increase further), finds no improving step
again (same point, same linearisation, same result), and takes no step
again -- a genuine, stable FIXED POINT of the iteration map, not a slow
approach to one. This explains BOTH observations at once: why the
residual is bit-identical at iteration 150 to iteration 30 (literally
the same state, re-evaluated), and why each iteration still takes real
wall-clock time (the full LM_MAX_TRIES x STEP_FRACTIONS grid of
expensive _merit() calls is still being run every iteration, just
without ever finding anything better) -- consistent with the ~600-900s
observed (vs ~50-130s when a point WAS still accepting occasional
steps within the original 30-iteration run, per the prior reports'
timing data).

This is consistent with, not contradictory to, the prior four reports'
findings: reports/phase7_solver_instability_fix_report.txt's Step 1
diagnosis (a shared trust-region clip conflating the constraint-
correcting and measurement-fit step components) explains WHY no
improving step exists in the first place at these points -- a more
iterations budget cannot help a map that has already reached one of
its own fixed points, regardless of how many further times it is
evaluated.

probed from five independent angles (criterion looseness, LM damping
symmetry, two trust-region restructurings, a calibrated accept-ratio
test, and now budget size) without a committable fix emerging from any
of them.
