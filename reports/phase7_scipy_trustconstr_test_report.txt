HEADLINE RESULT: scipy.optimize.minimize(method='trust-constr') --
a mature, independently-implemented trust-region SQP solver, given
the SAME problem (same WLS objective, same hard zero-injection
constraints, same analytic Jacobians, reused unmodified) -- ALSO fails
to converge at all 6 pilot points (0/6 under the 1.0 kvar threshold).
But it does so DIFFERENTLY and INFORMATIVELY: it is dramatically
faster (~2.5s/point vs 50-900s/point for the hand-rolled solver, a
20-350x speedup) and, most importantly, it lands on the EXACT SAME
constraint_residual_inf (86.154295, to 6 significant figures) at ALL
SIX points, regardless of which of 6 genuinely different measurement
datasets (different timestamps, different load regimes) it was asked
to fit. This is the single most informative finding across the whole
seven-report series: an INDEPENDENT solver implementation, starting
from the SAME flat start, reaches the SAME numeric infeasibility
REGARDLESS OF THE DATA -- strong, direct evidence that the bottleneck
is a property of the CONSTRAINT SET/JACOBIAN near this starting region,
not of any particular solve method (the hand-rolled one OR this one)
and not of which real-world measurements are being fit. Per the task's
own decision point, this is the "fails similarly... the problem is
likely in the Jacobians/constraint feasibility itself" branch --
reported plainly, not run further. estimation/state_estimator.py is
UNTOUCHED (this is a wholly separate, new code path, per the task's
own instruction); the full 30-point sample and pytest re-run were NOT
executed (no need -- nothing in state_estimator.py changed, and the
decision point explicitly does not ask for them on this branch).

STEP 1 -- THE NEW SOLVE PATH
======================================================================
New file: estimation/state_estimator_scipy.py. Does NOT import from,
call, or modify estimation/state_estimator.py in any way -- confirmed
by grep (no cross-import) and by estimation/state_estimator.py's own
unchanged line count (559, identical to every prior report's starting
point) after this task.

Reuses, unmodified:
  - observability.estimator_model.build_estimator_model (SAME model
    construction every report in this series has used).
  - observability.jacobian.build_jacobian (the SAME analytic Jacobian
    -- one call per queried point returns BOTH the measurement-row
    Jacobian H and the constraint-row Jacobian C in one pass, exactly
    as estimation.state_estimator.StateEstimator's own _merit() does).
  - observability.state_vector.complex_v_from_state (same forward-
    voltage construction).
  - The SAME diagonal state-scale preconditioner (x = s*y, s = each
    V-node's own V_base for the voltage block, 1.0 for the angle
    block) estimation/state_estimator.py already applies, for the
    identical reason: the state mixes actual volts (~2000-2500) and
    radians (~0-2).

New construction (the ONLY new code):
  fun(y)    = sum(W * (z - h_meas(s*y))^2)             -- WLS objective
  grad(y)   = s * (-2 * H_meas^T @ (W * (z - h_meas(s*y))))  -- chain rule through x=s*y
  cons_fun(y) = h_zi(s*y)                                -- target 0 (hard constraint)
  cons_jac(y) = C * s[None, :]                           -- SAME "Cs" matrix
                                                             the hand-rolled solver computes
  constraint = NonlinearConstraint(cons_fun, 0.0, 0.0, jac=cons_jac)
  result = minimize(fun, y0, jac=grad, method='trust-constr',
                     constraints=[constraint], options={...})

A single-point cache (keyed on exact y bit-equality) avoids redundant
Jacobian builds when scipy queries fun/grad/the constraint jac
separately at the same y, which it frequently does.

======================================================================
THE KEY FINDING -- IDENTICAL RESIDUAL ACROSS 6 DIFFERENT DATASETS
======================================================================
All six pilot points -- spanning low, mid, and high load regimes, at
six different real timestamps with six genuinely different
measurement vectors z -- converge to constraint_residual_inf=86.1543
to 6 significant figures (86.154295/86.154295/86.154296/86.154296/
86.154295/86.154296 -- the tiny last-digit variation is float64
rounding noise, not a real difference). This cannot be explained by
"the measurement data happens to produce a similar outcome at each
point" -- the prior hand-rolled solver's OWN results at these same 6
points range from 84.7 to 110.5 kvar, a real, data-dependent spread.
trust-constr's identical result across all 6 is the signature of a
STRUCTURAL property of the constraint manifold itself (the set of x
satisfying c(x)=0, or more precisely, how close to it the solver's own
Lagrangian-merit stationarity condition can get FROM A FLAT START)
dominating over whatever the measurement data is pulling toward. This
is the most direct evidence in this entire seven-report series that
the limiting factor is the CONSTRAINT SET / its JACOBIAN near this
operating region, not: the hand-rolled solver's specific construction
(reports 2-6), nor the specific measurement data at any one timestamp
(this report, directly, by elimination).

possibly not limited to) the near-zero-impedance regulator and switch
