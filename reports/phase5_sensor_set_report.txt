PART A -- MINIMUM SENSOR SET
======================================================================

----------------------------------------------------------------------
1. Mandatory base (not searched over)
----------------------------------------------------------------------
Three categories are NOT optional "sensors" being traded off against
each other -- they are structurally necessary by construction, per D2/
D4's own framing, and are held fixed throughout this search:
  - 106 meter P,Q entries (multiphase registry variant, Phase 4's
    already-justified decision -- not re-litigated here)
  - 366 zero-injection equality constraints (free, exact, Sha25 Sec II)
  - 84 pseudo-measurements at the 42 unmetered loads (real, unmeasured
    consumption -- see Part B for the sigma estimate now used here)

  BASE = 556 rows.

----------------------------------------------------------------------
2. BASE alone already reaches full rank -- but is not yet redundant
----------------------------------------------------------------------
  rank(H) = 553 / 553  (BASE ALONE, no head/branch/V at all)
  n_critical = 5

  Critical measurements at BASE:
    PSEUDO_s107b_P   PSEUDO_s107b_Q
    PSEUDO_s113a_Q
    PSEUDO_s114a_Q
    PSEUDO_s2b_Q

All five are pseudo-measurements at unmetered loads on buses 2, 107,
113, 114 -- electrical extremities with no alternate path in BASE alone
to cross-check their injection. This is the honest, narrower
observation Phase 4's "search the maximal config" framing did not
surface: reaching rank=553 and reaching a GENUINELY REDUNDANT (BDD-
usable) configuration are two different thresholds, and only the
second is what actually protects these five measurements from an
undetectable single-point attack.

----------------------------------------------------------------------
3. The minimum addition that eliminates all criticality
----------------------------------------------------------------------
Searched in RES.md D4 Sec 4.3's cumulative priority order (|V| at
meters -> substation head, sub-searched by quantity type -> branch),
via observability/minimum_sensor_set.py (a committed, reusable module,
not a one-off script -- reproduced independently below):

  Candidate                    entries   n_critical after   verdict
  meters_V (all 53)                53          7            WORSE, redundant
  head_P_Q only                     6          0            MINIMUM -- stop here
  head_V only                       3          5            no help, redundant
  head_I only                       3          5            no help, redundant
  head_full (P,Q,V,I)              12          0            redundant (head_PQ alone suffices)
  branch_full (165)               165          0            redundant (alternative, far less efficient)

  MINIMUM SENSOR SET = BASE (556) + HEAD_P_A/B/C, HEAD_Q_A/B/C (6)
                      = 562 total rows
                      rank = 553/553, n_critical = 0

Only 6 additional registry entries -- the substation head's P,Q per
phase -- are strictly required beyond the mandatory base to reach the
same full-rank, zero-critical result Phase 4's 786-row maximal
configuration achieved. |V| at meters (53 entries) is not just
unneeded but COUNTERPRODUCTIVE for this specific goal: adding it to
BASE alone shifts the critical set to 7 (from 5) -- a real, if minor,
illustration that adding measurements is not always monotonically
beneficial to the CURRENT critical-measurement identification once
near-degenerate structure is present (a mathematical curiosity of which
specific rows the removal-test flags, not a physical property; total
observability is never reduced by adding a row). Head's VOLTAGE and
CURRENT quantities individually do nothing for these 5 -- only the
POWER-balance constraint at the substation (P_head, Q_head) supplies
the missing redundant path, via Kirchhoff's current law tying the
substation's total throughput to the sum of everything downstream,
including these leaf buses.

----------------------------------------------------------------------
4. Minimum vs. deployed -- these are different questions, both answered
----------------------------------------------------------------------
This report answers "what is the smallest addition that closes the
rank/criticality gap" precisely: HEAD_P_Q, 6 entries. RES.md's own
Phase 5 "Out" line ("substation head x3phi, 6-12 branch units, |V| at
meters") asks for something BROADER, justified by DIFFERENT criteria
D4 Sec 4.3 states explicitly and this report does not override:
  - Full head (P,Q,V,I) is "operationally the single highest-value
    sensor... nearly free to add" -- V and I give real-time cross-check
    value even though they don't move rank/criticality here.
  - Branch units give "measurement redundancy... to validate the
    dataset and identify/eliminate bad data" (Youssef Sec II) -- a bad-
    data-detection argument, not a rank argument; RES.md's own 6-12-
    unit range already anticipates most of the 165-row branch group is
    unnecessary for rank, consistent with what this search independently
    confirms (0 of 165 rows needed for rank/criticality once head_PQ is
    present).
  - |V| at meters is "free in a real AMI... directly constrains the
    voltage half of the state vector" -- a conditioning/cross-check
    argument, not a rank one.
This report does NOT change config/sensor_registry_multiphase.json's
"enabled" flags -- doing so would change what streaming/producer.py
actually publishes (Phase 3's live pipeline), which is a deployment
decision beyond "search for the minimum and report exactly which
entries are required and which are redundant" as asked. Flagged
explicitly under Known limitation / next step, not silently skipped.

PART B -- PSEUDO-MEASUREMENTS AT THE 42 UNMETERED LOADS
======================================================================

----------------------------------------------------------------------
1. sigma_pseudo -- estimated, not asserted
----------------------------------------------------------------------
Method (observability/pseudo_measurements.py), the "minimum acceptable"
RES.md names -- empirical per-node, per-time-bucket variance from held-
out historical data:
  1. Each unmetered load's dataset/node_loads_91/ series (IDEAL corpus,
     60 days, 1-min resolution) is split 75/25 into TRAIN (45 days) and
     HELD-OUT (15 days).
  2. Bucketed by hour-of-day (24 buckets/node) -- captures the dominant
     diurnal load shape without a richer model.
  3. The pseudo-measurement VALUE for a given hour is the TRAIN-bucket
     mean P,Q -- what a static, offline generator would predict.
  4. sigma_pseudo for that (node, hour) is the sample std of the HELD-
     OUT bucket's ACTUAL values around the TRAIN-derived mean -- an
     honest out-of-sample estimate, not the optimistic in-sample
     residual a train-only variance would give.
Reported sigma_pseudo (mean across the 24 hour-buckets) for all 42
unmetered loads, sorted, ranges 27.7% to 42.1% of that node's own mean
P (median ~34%) -- genuinely per-node, not a copy-pasted constant (56
distinct values across 42 x 2 quantities, confirmed by
tests/test_pseudo_measurements.py). Full 42-node table:
artifacts/20260829T165146Z/phase5_sensor_set/sigma_pseudo_summary.json;
per-hour detail (24 buckets x 42 nodes):
artifacts/20260829T165146Z/phase5_sensor_set/sigma_pseudo_per_hour.json.

Sample (lowest, median, highest sigma-fraction nodes):
  s102c   mean_p=20.03 kW   sigma_p=5.95 kW   (29.7%)
  s113a   mean_p=40.85 kW   sigma_p=13.69 kW  (33.5%)
  s95b    mean_p=20.09 kW   sigma_p=8.46 kW   (42.1%)

This replaces the flat SIGMA_FRAC_PSEUDO=0.10 placeholder Phase 4's own
observability/sweep.py used (documented there at the time as
"not asserted as the Phase-5 answer") -- observability/sweep.py's
build_pseudo_entries() now calls
observability.pseudo_measurements.build_pseudo_entries_with_estimated_sigma()
directly; sweep._sigma_for() prefers an entry's own pre-estimated sigma
when present, falling back to the flat-fraction rule only for meter/head/
branch entries that were never estimated this way.

----------------------------------------------------------------------
2. Static, offline-computed -- stated as a deliberate security property
----------------------------------------------------------------------
This generator NEVER conditions on live measurements -- it is computed
once from historical corpus data, before any live telemetry (attacked
or not) exists, and does not retrain or re-derive its (mean, sigma)
tables at inference time.

Ald25's own pseudo-measurement generator (WaveNet-LSTM, Monte Carlo
dropout for its own sigma estimate) consumes LIVE main-branch-flow
currents as an input feature. If an attacker manipulates those upstream
measurements, Ald25's generator LAUNDERS attacker-influenced signal
into what the estimator treats as an INDEPENDENT pseudo-measurement --
a circularity channel Ald25 never considers (the paper is non-
adversarial throughout). This design's offline, historical-only pseudo-
measurements are STRUCTURALLY IMMUNE to that channel: nothing an
attacker does to Layer-2 telemetry at run time can change what
observability/pseudo_measurements.py predicts for a given (node, hour),
because the prediction was fixed at generation time. This is framed
here as a DELIBERATE SECURITY CHOICE, per RES.md's explicit instruction
-- not an accuracy shortfall relative to Ald25's materially lower MAE
(0.059 vs. a GMM baseline's 0.241 on irregular loads) -- both designs
solve different problems; this one additionally refuses a specific
attack surface Ald25's does not defend against.

Residual exposure, acknowledged rather than hidden: STALE-MODEL DRIFT.
A pseudo-measurement generator fixed at one 60-day snapshot becomes a
worse predictor as real consumption patterns shift over time (seasonal
change, new appliances, behaviour change) -- this would show up as
sigma_pseudo becoming too optimistic relative to the true current
spread, a data-freshness problem to monitor and periodically re-
estimate against, not a live-data attack surface.

----------------------------------------------------------------------
3. Distinct from zero-injection -- verified, not just asserted
----------------------------------------------------------------------
Zero-injection (Phase 4, observability/zero_injection.py): load-FREE
phase-nodes, P=Q=0 known EXACTLY, enforced as hard equality constraints.
Pseudo-measurements (this phase, observability/pseudo_measurements.py):
the 42 UNMETERED LOAD nodes, which have REAL, nonzero, just-unmeasured
consumption, estimated with an honest nonzero sigma from historical
data. Kept structurally distinct, not just in prose:
  - Separate modules, separate id namespaces (ZI_* vs. PSEUDO_*) --
    tests/test_pseudo_measurements.py::
    test_pseudo_and_zero_injection_use_disjoint_id_namespaces asserts
    both the id-prefix split AND that the two mechanisms' node sets are
    disjoint (no bus is ever both a zero-injection node and a pseudo-
    measurement node) against the REAL compiled circuit, not a mock.
  - Different treatment in the rank/conditioning machinery
    (observability/sweep.py): zero-injection rows are Lagrangian
    equality constraints (in the rank test, excluded from H^T W H);
    pseudo-measurement rows are ordinary weighted measurements (in
    both the rank test AND H^T W H, now weighted by their genuinely
    estimated sigma rather than a placeholder).

LIMITATIONS
======================================================================
  - The minimum sensor set (Sec Part A.3) is not deployed -- config/
    sensor_registry_multiphase.json's "enabled" flags are unchanged.
    Wiring the 6 head_P_Q entries (or RES.md's broader recommended set)
    into the live producer/consumer pipeline (streaming/producer.py
    does not currently measure or publish head telemetry at all) is a
    deployment decision this report deliberately did not make --
    flagged under Known limitation / next step.
  - sigma_pseudo's hour-of-day bucketing (24 buckets) is the "minimum
    acceptable" method RES.md names, not the richer Monte-Carlo-dropout
    learned-generator approach Ald25 uses; a finer time resolution (or
    day-of-week interaction) was not attempted, judged unnecessary
    given 900+ held-out samples per bucket already gives a stable
    estimate.
  - The train/held-out split (75/25, 45/15 days) is a reasonable,
    stated choice, not validated against alternative splits.
  - The critical-measurement search (Sec Part A.3) tested candidates in
    RES.md's stated priority order and stopped at the first sufficient
    one (head_P_Q) -- it does not claim head_P_Q is the UNIQUE minimum
    (e.g. some smaller ad hoc combination of individual branch segments
    might also work) -- only that it is the smallest of the CATEGORIES
    RES.md's own D4 Sec 4.3 table names, tested in its own priority
    order, which is what this task asked for.
