======================================================================
RES.md D10 Phase 6 -- Normal-Operation Corpus Report
======================================================================

Scope: generate a clean, labelled baseline of normal (unattacked)
telemetry across the full 60-day IDEAL corpus window, split by TIME
(never randomly), with the full x_true ground-truth state persisted
per timestamp for Phase 11's later impact quantification.

----------------------------------------------------------------------
Decision: deploy the minimum sensor set now
----------------------------------------------------------------------
Phase 5 found the minimum sensor set (106 multiphase meter P,Q + 6
substation head P,Q = 112 rows, on top of zero-injection + pseudo-
measurements, achieving rank=553/553 with 0 critical measurements) but
left it undeployed. Phase 6 took option (a): DEPLOYED it before
generating anything, by flipping HEAD_P_A/B/C and HEAD_Q_A/B/C's
"enabled" flag from false to true in
config/sensor_registry_multiphase.json (verified: exactly those 6,
total enabled count 106 -> 112). Rationale, as the task itself states:
generating against an undeployed configuration would mean re-
generating later when it is actually deployed, and the minimum set is
the one Phase 5 showed has zero critical measurements -- it should be
the one everything downstream is built on, not a placeholder.

Two tests in tests/test_streaming.py hardcoded the pre-deployment
enabled count (106) for the multiphase variant; updated to 112 with an
explicit comment pointing at this decision (not silently patched to
pass). config/sensor_registry.json (the default, non-multiphase
variant) is untouched -- this deployment decision only concerns the
adopted (multiphase) variant.

Zero-injection (366 constraints) and pseudo-measurements (84, sigma
estimated in Phase 5) are NOT registry entries and are not part of
this corpus's telemetry files -- per RES.md D2/D4, they are estimator
INPUT (Phase 7's concern), not sensor readings a corpus of
"telemetry.raw content" would contain. Confirmed still structurally
distinct from meter/head telemetry (Phase 5's own test coverage).

----------------------------------------------------------------------
What was generated
----------------------------------------------------------------------
validation/generate_phase6_corpus.py runs the SAME L1 ground-truth +
L2 sensor-layer machinery streaming/producer.py's Producer class uses
(compile_feeder, drive the 49 representative loads from
dataset/node_loads_91/, solve once per timestamp, measure z via
sensors.sensor_layer.build_measurement_dict() in one ordering-
consistent pass over the 112 enabled registry entries) -- but writes a
flat, wide per-timestamp record directly to files instead of Kafka
messages. This is a deliberate scope boundary, not an oversight:
extending Producer's per-METER message schema (and streaming/
consumer.py's meter-COUNT-based window-completion check) to also carry
head telemetry, which has no load_name, would require changing the
live wire protocol and consumer buffering logic -- a Phase-3-amendment-
scale change this phase does not attempt. What Phase 6 needs is
queryable per-timestamp training data, which this script produces
directly; the live pipeline's own head-telemetry wiring is left for a
future phase (see Known limitation).

No live Kafka broker was available in this environment (consistent
with every phase this session) -- generation used the same direct-
replay methodology Phase 0/3/4/5 established, exercising the real
sensor-layer code, not a re-implementation.

Sensor noise: add_noise=True (the production default, sigma per
sensors/generate_registry.py's per-entry convention), ONE continuous
RNG stream (seed=42) across the full 60-day run -- not reset per split,
matching how one real, continuous telemetry stream would behave (a
train/val/test split is a downstream analytical partition of one
timeline, not three independently-generated processes).

----------------------------------------------------------------------
Time-based split -- never random
----------------------------------------------------------------------
Split by contiguous CALENDAR DAY (computed from the corpus's own real
timestamps, not hand-calculated), 70/15/15:

  train:  2018-04-04 .. 2018-05-15   (42 days, 60,480 rows)
  val:    2018-05-16 .. 2018-05-24   ( 9 days, 12,960 rows)
  test:   2018-05-25 .. 2018-06-02   ( 9 days, 12,960 rows)

  60 days total, 86,400 timestamps -- exactly the full available
  window, no sampling.

Contiguity and non-leakage verified by test
(tests/test_phase6_corpus.py::test_split_is_contiguous_by_calendar_day_not_random):
split labels appear in strict train*-val*-test* order with no
interleaving, which a correct day-boundary split guarantees and a
random shuffle would violate; every row is covered exactly once
(test_split_covers_every_row_exactly_once); the realised ratios are
70.0% / 15.0% / 15.0% (test_split_ratio_is_approximately_70_15_15).

----------------------------------------------------------------------
Sensor configuration used
----------------------------------------------------------------------
Stated explicitly, not an ambiguous mix: config/sensor_registry_
multiphase.json, 112 enabled entries -- 106 meter P,Q (49 representative
meters, 4 additional B/C-phase entries at S47/S48 per the Phase 3
multiphase variant) + 6 substation head P,Q (HEAD_P_A/B/C, HEAD_Q_A/B/C,
Phase 5's deployed minimum addition). Every telemetry column in
{train,val,test}_telemetry.csv is one of these 112 registry ids, built
in the single ordering-consistent pass sensors/sensor_layer.py's
build_measurement_dict() performs -- the same registry-traceability
property Phase 3 established and tested.

----------------------------------------------------------------------
x_true persisted per timestamp
----------------------------------------------------------------------
observability/state_vector.py's extract_solved_state() (new this
phase) reads the ACTUAL solved circuit's per-node voltage magnitude and
angle via dss.Circuit.AllBusVolts(), in the SAME (v_index, delta_index)
553-dimensional layout Phase 4's flat-start state vector uses -- so
Phase 7's estimator can compare x_hat against x_true with one
consistent state definition across phases, not a second ad hoc one.
Cross-checked against get_solution_metrics()'s own independently-
computed v_pu_min/max (tests/test_phase6_corpus.py::
test_extract_solved_state_v_pu_matches_get_solution_metrics, agrees to
1e-6) -- not just internally self-consistent.

Saved as {split}_x_true.npz (numpy compressed: x_v shape
(n_rows, 278) in actual volts, x_delta shape (n_rows, 275) in radians,
plus the v_index/delta_index name->column mappings for later lookup).
CSV was not used for this file -- 553 columns x 86,400 rows of float64
is a genuinely large, dense numeric array (~380 MB uncompressed across
all splits) that compresses well and is far faster to load for Phase 7
as a numpy array than as text.

----------------------------------------------------------------------
Corpus statistics
----------------------------------------------------------------------
CONVERGENCE: 100% across all three splits -- 86,400/86,400 timestamps
converged, 0 failures (independently re-confirmed via
{split}_ground_truth.csv's own "converged" column, not just the
generation run's own summary line).

NO NaNs, NO GAPS (acceptance criterion, checked directly, not assumed):
  split   telemetry(114 cols)  ground_truth  x_true(278+275 cols)  timestamp gaps
  train   0 NaNs               0 NaNs        0 NaNs                0
  val     0 NaNs               0 NaNs        0 NaNs                0
  test    0 NaNs               0 NaNs        0 NaNs                0

The task named a "known 7.2% partial-contribution minutes" finding
from Phase 1 to check against. No written record of that specific
figure was locatable in this repo (reports/phase1_data_layer_report.txt
predates the IDEAL-corpus swap and does not mention it), so it could
not be cross-referenced directly -- but the underlying concern (does
anything in the source data surface as NaNs or gaps in the generated
telemetry) is independently and directly verified clean above, across
the full 60-day window, not sampled.

PER-METER VALUE RANGES (train split, 49 representative meters):
  P columns: min=-0.918 kW, max=434.011 kW
  Q columns: min=-11.226 kvar, max=309.012 kvar
  Head columns (per phase): HEAD_P ranges roughly 490-3279 kW/phase,
  HEAD_Q roughly 23-1850 kvar/phase -- consistent with feeder-head
  totals reported since Phase 0/1 (~3490 kW nominal, ~1920 kvar).

NEGATIVE-P FINDING (investigated, not just noted): 27 of 49 meters show
at least one negative P_injection reading somewhere across 60,480 train
rows; in total 63 of 2,963,520 individual meter-timestep readings
(0.0021%) are negative, and every one is TINY (max magnitude 0.92 kW).
This is the expected, honest behaviour of a REALISTIC noisy AMI sensor
model (z = h(x_true) + e, e ~ N(0, sigma), sigma ~1% of the reading per
sensors/generate_registry.py): during a household's near-zero-
consumption minutes (overnight, vampire load only), Gaussian
measurement noise can occasionally push an already-small true reading
slightly negative -- exactly what a real smart meter's instrument noise
can do, and NOT clipping it at zero is the more honest simulation
choice (clipping would silently bias the noise distribution). This is
not a NaN, not a gap, and not a bug -- flagged here as a finding, per
CLAUDE.md's data-caution instinct, rather than silently smoothed over.

STATIONARITY (RES.md's own acceptance item, reported not assumed):
train-split feeder-head P, first half vs. second half:
  first half  (days 1-21):  mean=3768.92 kW, std=918.64 kW
  second half (days 22-42): mean=3569.72 kW, std=853.16 kW
A real, mild non-stationarity -- mean down ~5.3%, std down ~7.1% across
the 6-week train window. Consistent with genuine seasonal/behavioural
drift in real household consumption data (the IDEAL corpus is drawn
from actual UK households across April-May) rather than a data defect.
Reported honestly as "mildly non-stationary," not overclaimed as
stationary -- Phase 9's temporal predictor and Phase 12's ablations
should be aware a train-period baseline will drift somewhat by test
time even absent any attack.

PER-METER CORRELATION (RES.md's own acceptance item; also the Phase-1
"don't let the imposed correlation become a detector shortcut" concern,
re-checked against the NEW IDEAL-corpus-based telemetry): full 49x49 P
correlation matrix, train split --
  mean r = 0.576, median = 0.574, range [0.393, 0.780], std = 0.063
  0.0% of the 1,176 meter pairs exceed |r| = 0.9 (or 0.95)
Moderate, physically expected correlation (households share a common
diurnal shape -- everyone's load rises in the evening) with NO pair
anywhere near 1.0 -- confirms Phase 1's diversification goal holds in
this corpus: there is no suspiciously uniform correlation structure a
detector could exploit as a shortcut instead of learning genuine
attack signatures.

======================================================================
LIMITATIONS
======================================================================
  - The live streaming pipeline (streaming/producer.py,
    streaming/consumer.py) still only knows how to publish/consume
    per-meter messages -- it does NOT publish head telemetry, even
    though the registry now enables it. This corpus is generated by a
    dedicated script that reuses the same underlying sensor-layer
    mechanics, not by literally running the live Kafka pipeline end to
    end (no broker available, consistent with every phase this
    session). Wiring head telemetry into the live wire protocol is a
    separate, not-yet-scoped change.
  - The "7.2% partial-contribution minutes" fact named in the task
    could not be located in this repo's own written record to cross-
    reference directly; the corpus was verified NaN/gap-free directly
    instead of via that specific historical figure.
  - Sensor noise uses ONE fixed seed (42) for the entire 60-day run --
    reproducible, but means the noise realisation itself is not varied
    across multiple regenerations; re-running with a different seed
    would produce a different (but equally valid) noise draw.
  - Stationarity and correlation were reported for the train split (and
    a P-only, meter-only slice) as the representative check; val/test
    splits were confirmed clean (NaNs, gaps, convergence) but not
    separately re-characterised for stationarity/correlation, since
    they are held out specifically to be compared against train-period
    statistics later (Phase 9/12), not to be independently
    characterised now.
