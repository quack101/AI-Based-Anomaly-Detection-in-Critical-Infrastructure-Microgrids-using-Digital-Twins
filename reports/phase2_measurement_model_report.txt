1. h_abc(.) -- sensors/measurement_functions.py
----------------------------------------------------------------------
  Nine quantity types, each phase-resolved (reads one specific (node,
  phase) pair via OpenDSS's own NodeOrder/terminal indexing -- never an
  aggregate across phases, unlike the pre-existing get_load_telemetry()
  in simulation/opendss_utils.py, which sums across all phases of a
  load):
    P_injection, Q_injection        -- Sayghe eq. (14)-(15), load-bus
    V_magnitude                     -- direct, p.u. (reused for both
                                        meter |V| and substation-head |V|)
    P_flow, Q_flow                  -- Anwar eq. (17.5)-(17.6), branch
    I_magnitude_branch              -- Anwar eq. (17.7)
    P_head, Q_head, I_magnitude_head -- same forms applied to the
                                        Vsource element, sign-corrected
                                        to report power DELIVERED into
                                        the feeder as positive

  Each function reads the CURRENTLY SOLVED circuit only -- it does not
  solve or compile anything itself (compile_and_solve()/extract_all()
  is the caller's responsibility, same convention as core.ieee123_model).

2. SENSOR REGISTRY -- config/sensor_registry.json
----------------------------------------------------------------------
  Schema (RES.md D10 Phase 2's literal {id, node, phase, quantity,
  sigma, rate}, extended minimally): id, node, phase, quantity, sigma,
  rate, enabled, plus load_name (injection sensors) / element_name +
  element_kind (branch/head sensors, needed because a branch quantity
  has two endpoints, not one) / note (provenance).

  Built by sensors/generate_registry.py from:
  - simulation/representative_meters.json (the 49 meters)
  - core.ieee123_model.extract_all() (verified compiled-circuit Lines)
  - placement.feeder_context.FeederContext's main_feeder (the SAME
    backbone computation the placement work uses, per RES.md D4 4.3
    row 3's explicit instruction: "Use your existing backbone-coverage
    score to place these")

  CONTENTS, scoped exactly to what this phase justifies (D4 4.3):
    row 2 (substation head P,Q,|V|,|I| x3) -- 12 entries, disabled
    row 3 (branch P,Q,|I| at backbone Lines) -- 165 entries, disabled
    row 4 (|V| at existing meters) -- 49 entries, disabled
    row 6 (transformer sensors) -- NOT added; RES.md states no paper
      justifies this
    row 5 (PMUs) -- NOT added; explicitly optional/deferred
    row 0 (zero-injection) and row 1 (pseudo-measurements at the 42
      unmetered Loads) -- NOT sensor-registry entries. Neither is a
      sensor reading a solved circuit: row 0 is an exact algebraic fact
      about the network (Phase 4's estimator input), row 1 is a
      historical-data-derived estimator input (Phase 5's sigma_pseudo
      amendment), not a live measurement. Registering them here would
      have been the modelling error Anwar/Sayghe warn against
      (conflating pseudo-measurements with equality constraints, or
      either with a live sensor).

3. THE LAYER-1/LAYER-2 BRIDGE
----------------------------------------------------------------------
  sensors/sensor_layer.py's build_measurement_vector() is the ONLY
  place z is constructed: one pass over registry.enabled_entries(),
  per entry h_k(x_true) via measurement_functions.measure() [+ per-
  entry Gaussian noise using THAT entry's own sigma]. No other module
  in this codebase does this.

  NOT YET WIRED INTO THE LIVE PIPELINE -- stated plainly, not hidden:
  streaming/producer.py still reads from data/scaled_datasets (Phase 1,
  blocked) and does not import sensors/ at all yet. "No OpenDSS
  quantity reaches Kafka without a registry entry" is satisfied for
  what sensors/ itself can emit; making it true of the actual Kafka
  topic is explicitly Phase 3's job ("move the sensor layer into the
  producer" -- RES.md D10 Phase 3), not this phase's.

----------------------------------------------------------------------
4. THE JACOBIAN -- structure in place, not built (stated explicitly)
----------------------------------------------------------------------
  CHOICE: structure in place for Phase 4, not an analytic H now.
  WHY: h_abc(.) as implemented here reads a SOLVED circuit (the fast,
  correct path for publishing telemetry) -- it is not a symbolic
  function of a free state vector you can differentiate directly.
  Sayghe eq. (14)-(15) express P_i^mu/Q_i^mu as explicit algebraic
  functions of x=(V,delta) and the Y-bus's phase-pair blocks
  (P_i^mu = V_i^mu * sum_{j,eta} V_j^eta (G^{mu,eta}_ij cos(...) +
  B^{mu,eta}_ij sin(...)), generalising Sayghe eq. (2)-(3)); Phase 4
  should differentiate THAT algebraic form analytically, per measurement
  type, reusing the Y-bus already exposed by core.ieee123_model /
  placement.electrical_distance.get_system_y_index() (built from the
  SAME compiled-circuit source, same (node,phase) indexing this
  registry already uses) -- not finite-difference through repeated
  OpenDSS solves, which would be slower and worse-conditioned for a
  stiff AC power flow. Documented in measurement_functions.py's module
  docstring so Phase 4 doesn't have to re-derive this decision.

LAYER-BOUNDARY TEST -- tests/test_import_boundaries.py
----------------------------------------------------------------------
  test_no_ground_truth_circuit_access_outside_sensors: AST-parses every
  .py file under estimation/, detection/, evaluation/ (none exist yet)
  for imports of opendssdirect OR any codebase module that itself
  reaches a live circuit (core.ieee123_model, sensors.measurement_
  functions, sensors.sensor_layer, sensors.generate_registry,
  simulation.opendss_utils). sensors.registry is deliberately NOT
  forbidden -- it only loads/validates registry metadata (id, sigma,
  rate, enabled), never touches a circuit, so a future estimator
  reading sensor METADATA (e.g. to build W = diag(sigma^-2)) is fine;
  reaching the circuit itself is not. Passes vacuously now (the
  directories don't exist); test_restricted_dirs_do_not_exist_yet
  documents that fact explicitly so a future run that finds them
  existing is a visible signal to double check the boundary test is
  actually being exercised, not silently vacuous forever.

FINDINGS
----------------------------------------------------------------------
  1. 5 of the 49 metered loads are multi-phase (s35a: A,B; s47: A,B,C;
     s48: A,B,C; s76a: 2 phases; s65c: 2 phases) -- confirmed by direct
     inspection. Per RES.md's explicit "m=98" statement for the current
     configuration, this registry meters each such load's PRIMARY phase
     only (node_order[0]), matching the pre-existing pipeline's one-P/Q-
     per-meter convention. This is a genuine, documented under-coverage
     (those loads' other phases are unmeasured), not a bug -- extending
     any of these 5 to report every phase they touch is a cheap,
     one-entry-per-phase registry addition for a later phase, not done
     here because it would push m above the 98 this phase is scoped to.

  2. sigma values are a documented ASSUMPTION, not a literature-cited
     figure -- RES.md gives sigma_pseudo guidance (Phase 5, for the
     DIFFERENT row-1 pseudo-measurements) but no number for these live
     sensors. Used: 1% of each sensor's own noise-free reading for
     P/Q/|I|-type quantities, flat 0.5% of nominal (1.0 p.u.) for
     voltage. Both are conventional AMI/SCADA/instrument-accuracy
     orders of magnitude, not derived from a cited source -- flagged
     for review, not asserted as settled.

  3. 2 of the 21 backbone (main-feeder) hops (150-149, 160-67) matched
     no single Line element in build_branch_entries() -- both are
     regulator-collapsed hops in the topology graph (a transformer +
     a separate switch-Line, collapsed into one topology edge by
     FeederContext's regulator-helper-node logic). Correctly skipped,
     not an error -- "branch flow sensor" means a conductor per RES.md's
     own framing; the regulator/substation role is separately covered
     by the head entries.

LIMITATIONS
----------------------------------------------------------------------
  - Registry not wired into streaming/producer.py -- that is Phase 3.
  - Row-0 (zero-injection) and row-1 (pseudo-measurement) entries are
    intentionally absent from this registry; Phase 4/5 will need a
    DIFFERENT structure for them (not a "sensor" in this schema's
    sense, since they don't read a solved circuit at runtime the same
    way).
  - The Jacobian is structure-only, per the explicit Phase 4 hand-off
    documented in measurement_functions.py and restated above.
  - sigma values are a documented default assumption (Finding #2), not
    literature-derived -- worth revisiting if a cited figure surfaces.

UNBLOCKS
  - Phase 4 (observability analysis) can now build H_abc from a
    well-defined, ordered registry and the already-available Y-bus
    infrastructure (placement.electrical_distance.get_system_y_index()),
    with dim(z) and the (node,phase) indexing already fixed.
  - Phase 3 (streaming restructure) has a concrete sensors/ module to
    move into the producer.
  - Phase 5 (minimum sensor set) can enable specific registry entries
    (head, branch, |V|) via a pure config edit -- no code change needed,
    as required.

BLOCKS
  - Phase 4's actual H construction, rank/cond computation -- not
    started (out of this phase's scope; the structure is ready).
  - Phase 3's streaming rewire -- not started.
